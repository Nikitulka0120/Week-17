# Вопросы для самопроверки

1. Какие критерии вы использовали при разделении монолита на микросервисы (или при проектировании сервисов)?

Ответ: Главным критерием был принцип единой ответственности. Бизнес-логика и CRUD-операции с товарами сосредоточены в основном бэкенде (FastAPI), а сбор и хранение логов вынесен в отдельный микросервис log-svc. Такое разделение обеспечивает изоляцию сбоев: падение сервиса логирования не останавливает работу с товарами. Инициализация БД также вынесена в отдельный контейнер db-init, чтобы не смешивать жизненные циклы. Это позволяет в будущем масштабировать каждый компонент независимо.

2. Почему вы выбрали именно этот стек технологий (язык, БД, протоколы)?

Ответ: Python и FastAPI обеспечивают высокую скорость разработки и автоматическую генерацию OpenAPI-документации. PostgreSQL выбран как надежная реляционная база с поддержкой транзакций и ORM SQLAlchemy. В качестве протоколов используется REST для взаимодействия с фронтендом (прост в отладке через браузер) и gRPC - для межсервисного взаимодействия между backend и log-svc (бинарная сериализация через Protocol Buffers значительно эффективнее JSON). Для реального времени использован WebRTC DataChannel в связке с WebSocket-сигналингом - для одноранговой синхронизации состояния дашборда без нагрузки на сервер.

3. Как ваши сервисы справляются с ошибками (retry, circuit breaker, graceful degradation)?

Ответ: В бэкенде реализованы три уровня отказоустойчивости при взаимодействии с log-svc:
- Retry с экспоненциальной задержкой - при сбое отправки лога делается до 3 повторных попыток с паузами 0.5с, 1с, 2с между ними.
- Circuit Breaker - если сервис логирования выдает 5 ошибок подряд, цепь размыкается (состояние OPEN) на 30 секунд. В этом состоянии бэкенд вообще не пытается обращаться к log-svc, устраняя каскадные задержки. Через 30 секунд цепь переходит в состояние HALF-OPEN и делается пробный запрос.
- Graceful Degradation - при разомкнутом предохранителе или исчерпании попыток Retry лог пишется в консоль бэкенда ([FALLBACK LOG]), а все API-эндпоинты (CRUD, статистика) продолжают работу в штатном режиме без ошибок для пользователя.

4. Как организован деплой и обновление вашей системы без простоя (Zero Downtime)?

Ответ: Локально вся система запускается одной командой docker-compose up --build. Для развертывания в Kubernetes разработан Helm-чарт (директория helm/), структурированный по аналогии с week-13: два шаблонных файла (templates/deployment.yaml и templates/service.yaml) и три файла значений для разных сред (values-dev.yaml, values-stage.yaml, values-prod.yaml). Для сервисов backend и frontend настроена явная стратегия обновления RollingUpdate - при обновлении сначала создается новый под, проходит readinessProbe и liveness проверки, и только после успешного старта старый под удаляется. Это гарантирует Zero Downtime при раскатке обновлений.

5. Что было самым сложным в интеграции всех компонентов вместе?

Ответ: Довольно сложной оказалась правильная настройка автоматической генерации кода из protobuf файлов при сборке Docker образов. Также потребовалось решить проблему с порядком запуска контейнеров, настроив healthcheck в PostgreSQL и выделив инициализацию базы в отдельный db-init сервис.

6. Что бы вы улучшили, если бы у вас был еще месяц?

Ответ: В первую очередь я бы хотел сделать более красивый и современный фронтенд, так как текущая визуализация довольно базовая. К обновленному интерфейсу я бы прикрутил новые разделы сайта: добавил бы поиск по товарам, систему фильтрации и красивое отображение в виде карточек. Также можно было бы доработать бэкенд для поддержки пагинации, чтобы новый фронтенд работал быстро даже при большом количестве данных.
